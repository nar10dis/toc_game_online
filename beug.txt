====================================================

Comment j'ai testé :
- ~40 comptes créés via l'API (emails en @test.fr / @t.fr), tout passe par nginx (https://localhost:8443)
- scripts HTTP : entrées pourries, doubles clics, requêtes en parallèle, tokens volés/périmés
- clients socket.io : vraie partie 2 humains + 2 bots avec déco/reco au hasard, actions bidon, spam du chat
- Chromium sans tête : clique partout au hasard, F5, bouton retour, hors-ligne, 2 onglets, largeur mobile
Tout ce qui est marqué [REPRO] a été reproduit, pas juste supposé en lisant le code.

Légende : !!! = bloquant / risque de note éliminatoire   !! = un correcteur le verra   ! = finition

!!! BLOQUANT / SÉCURITÉ
=====================================================================

1. [CORRIGÉ] "Create game" / "Join game" depuis le menu : le lobby reste bloqué sur "Connecting..." [REPRO]
   -> autoConnect: false enlevé de chatSocket.ts, vérifié dans le navigateur (lobby sans F5, chat sans doublon).
   - Il faut faire F5 pour voir la salle d'attente. C'est le parcours principal du jeu.
   - Cause : frontend/src/sockets/chatSocket.ts crée la socket avec { autoConnect: false }.
     Dans socket.io-client, cette option est retenue par le Manager, PARTAGÉ par toutes les
     sockets du même serveur. Le chat global est créé en premier (sur /menu), donc la socket du
     jeu (gameSocket.ts, io({ path })) créée ensuite ne se connecte jamais.
     (node_modules/socket.io-client/build/cjs/socket.js:127 : `if (this.io._autoConnect)`)
   - Si on ouvre /lobby directement (F5), la socket du jeu est créée en premier et tout marche.
   - Fix simple : dans gameSocket.ts, appeler socket.connect() juste après io(...)
     (ou enlever autoConnect: false du chat).

2. [CORRIGÉ] Plus de 4 joueurs dans une partie, sièges en double [REPRO]
   -> le joueur est ajouté en mémoire avant l'await Prisma : 6 joins simultanés = 3 acceptés, 3 refusés, sièges {0,1,2,3}.
   - 5 personnes cliquent "Join" en même temps sur une table où il ne reste que 3 places : 5 x 201.
   - En base, la partie 6 a 6 joueurs, sièges {0,1,1,1,2,2}.
   - Cause : game.service.ts joinGame() vérifie "places libres" puis fait un `await prisma...`
     AVANT d'ajouter le joueur en mémoire, et calcule le siège depuis l'ancien état.
   - Fix : ajouter le joueur en mémoire (commit) AVANT l'await, ou un verrou par partie.

3. !!! Les cookies de session de tout le monde sont lisibles sans mot de passe [REPRO]
   - Les logs du backend (pino-http) contiennent les en-têtes complets, cookie jwt ET refresh_token.
   - Ils partent dans Elasticsearch, ouvert sur http://localhost:9200 sans authentification
     (xpack.security.enabled=false). `curl 'localhost:9200/_search?q=refresh_token'` renvoie des
     refresh tokens valides 7 jours, donc on peut se connecter sur le compte de n'importe qui.
   - Kibana (5601) aussi est ouvert sans login.
   - Fix : `redact: ['req.headers.cookie', 'res.headers["set-cookie"]']` dans la config pino
     (backend/src/config/logger.config.ts), et ne pas publier 9200/5601 (ou activer la sécurité).

4. !!! Secrets dans git
   - .env (racine) est commité, avec POSTGRES_PASSWORD (historique depuis le commit 38339ed).
   - Il n'y a PAS de .gitignore à la racine : 118 fichiers de frontend/.next sont commités aussi.
   - En correction, "des identifiants dans le repo" est souvent éliminatoire.
   - Fix : .gitignore (.env, .next, node_modules, uploads), `git rm --cached`, et changer les mots
     de passe (ils restent dans l'historique).
   - Au passage : .env contient POSTGRES_PASSWORD et POSTGRES_DB en double.

5. !!! Erreurs 500 sur des cas banals [REPRO]
   - Inscription avec un email déjà pris : 500 (au lieu de 409)
   - Inscription avec un pseudo déjà pris : 500
   - Double clic sur "Sign up" : le 2e clic donne 500
     -> auth.service.ts register() ne gère pas l'erreur Prisma P2002 (profile.service.ts le fait déjà
        pour le pseudo, on peut copier).
   - GET /api/profile/99999999999999 : 500 (nombre trop grand pour un Int Postgres)
   - Compte supprimé mais jwt encore valide (15 min) -> POST /api/game : 500 (clé étrangère)
   - Socket 'action' avec un payload null : crash "Cannot read properties of null (reading 'gameId')"
     (game.gateway.ts handleAction : body.gameId sans `?.`)

7. [CORRIGÉ] On peut être dans plusieurs parties à la fois / perdre sa partie en cours [REPRO]
   -> une seule partie à la fois (409 sur create/join, double clic compris). Le menu affiche
      "Resume game" / "Quit game" quand on a une partie en cours. Quit : en salle d'attente on libère
      le siège (le suivant devient hôte), en partie l'IA prend la place pour de bon.
   - "Create game" pendant une partie en cours : nouvelle partie créée, et /play montre maintenant
     la nouvelle. L'ancienne continue avec l'IA à notre place, sans moyen d'y revenir.
   - Double clic sur "Create game" : 2 parties créées.
   - Le menu ne propose pas de "reprendre ma partie".
   - Fix : refuser create/join si findGameOfUser() renvoie une partie pas finie (409), ou
     rediriger vers elle.

8. [CORRIGÉ] Pas de bouton "Quitter" dans le lobby
   -> bouton "Quit game" dans le lobby (et dans le menu) : le siège est libéré, le suivant devient hôte.
      Reste : la suppression de compte de l'hôte ne passe pas par leaveGame().
   - Un joueur qui a rejoint garde son siège pour toujours, même s'il part au menu.
   - Si l'hôte supprime son compte, le lobby reste là et personne ne peut le lancer
     ("Only the host can lock the team").

     413 avec une page HTML nginx (le front affiche juste "Something went wrong.").
   - Fix : `client_max_body_size 2m;` dans nginx/nginx.conf.
